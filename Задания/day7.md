# Тема: абстрактные классы

Смотри на нашу иерархию Enemy → Zombie/Vampire/etc. Возникает вопрос: а имеет ли смысл вообще создавать объект просто Enemy, без указания конкретного типа? По логике игры — нет, "противник вообще, без типа" не существует, существуют только конкретные виды. Enemy там нужен исключительно как общий каркас для остальных классов, а не как то, что реально создаётся само по себе.

## Абстрактный класс — это способ явно запретить создание объектов напрямую от базового класса, разрешив создавать объекты только от его наследников. Плюс можно обязать все наследники реализовать определённые методы.

Синтаксис (используется модуль abc — Abstract Base Classes):

python
from abc import ABC, abstractmethod

class Enemy(ABC):
    def __init__(self, health):
        self.health = health

    @abstractmethod
    def move(self):
        pass   # тело неважно, это просто "требование" — потомок обязан это реализовать

Что здесь происходит:

Enemy(ABC) — наследование от специального класса ABC, это и превращает Enemy в абстрактный.
@abstractmethod — это декоратор (специальная пометка перед методом, меняющая его поведение; синтаксис @имя — мы отдельно декораторы подробно разбирать не будем, для тебя пока достаточно знать, что это способ "пометить" метод особым образом). Он говорит: "любой класс, наследующий от Enemy, обязан реализовать move() — иначе Python не даст создать объект такого класса".

Если попробовать:

python
e = Enemy(30)   # TypeError! Нельзя создать объект абстрактного класса напрямую

А если Zombie(Enemy) не реализует move() — тоже будет ошибка при попытке создать Zombie(...). Это заставляет тебя не забыть реализовать обязательное поведение в каждом наследнике — полезная защита от собственных ошибок в большом проекте с 5 видами врагов.

## Тема: dataclasses

Заметь, как много раз мы писали одинаковый скучный код вида:

python
def __init__(self, name, health, strength):
    self.name = name
    self.health = health
    self.strength = strength

Когда класс — это просто "контейнер данных" без сложной логики, Python предлагает укороченный способ через декоратор @dataclass:

python
from dataclasses import dataclass

@dataclass
class Item:
    name: str
    item_type: str
    value: int

Это автоматически создаёт __init__, который принимает name, item_type, value и сохраняет их как атрибуты — ровно то, что мы писали руками, но без ручного кода. Плюс автоматически появляется красивый __repr__ (как объект выглядит при печати) и сравнение объектов по значениям.

Обрати внимание на синтаксис name: str — это аннотация типа (type hint): не строгая проверка (Python не заставит тебя передать именно строку), а подсказка для тебя, для IDE и для других разработчиков, какой тип ожидается. В School 21 это хороший тон — писать аннотации, особенно в доменных сущностях типа Item.

@dataclass идеально подходит для простых сущностей вроде Предмет, Комната, Коридор из задания — там в основном данные, минимум поведения. А для Character/Enemy, где много методов с логикой (attack, move), обычный класс с __init__ уместнее.

## Тема: композиция vs наследование

Это важный архитектурный выбор, который часто путают новички.

Наследование отвечает на вопрос "это — разновидность того-то?" (is-a). Zombie — это разновидность Enemy. Cat — разновидность Animal. Это уместно.

Композиция отвечает на вопрос "это содержит в себе то-то?" (has-a). Персонаж содержит рюкзак — но персонаж не является разновидностью рюкзака. Это принципиально разные отношения, и подставлять наследование туда, где нужна композиция — частая ошибка новичков.

Плохо (наследование там, где не нужно):

python
class Character(Inventory):   # Персонаж — это разновидность рюкзака?? Бессмыслица
    ...

Правильно (композиция):

python
class Inventory:
    def __init__(self):
        self.items = []

class Character:
    def __init__(self, name, health):
        self.name = name
        self.health = health
        self.inventory = Inventory()   # Character СОДЕРЖИТ Inventory как атрибут

Теперь персонаж.inventory.items — обращение через "точку дважды": сначала к атрибуту inventory объекта персонаж, потом к атрибуту items уже внутри объекта Inventory. Это и есть решение той путаницы с "рюкзаком-списком-словарей", которая была в твоём боевом коде — вместо голого списка inventory = [], болтающегося отдельно, теперь это полноценный объект со своей логикой (add_item, remove_item, ограничение "максимум 9 предметов каждого типа" может быть методом именно этого класса).

Общее правило в индустрии: "предпочитай композицию наследованию" (composition over inheritance) — наследование мощный инструмент, но легко перегружается на 3-4 уровня и превращается в путаницу; композиция обычно даёт более гибкую и понятную структуру.
